## 2. ❌ 一條被退掉的假工單：「案例圖仍是 JPG，該轉 WebP」

§8 第 4 列寫「首頁下方案例圖仍是 JPG」。**驗證後發現這對訪客完全不成立。**

`next.config.ts` 早就設了 `formats: ["image/avif","image/webp"]`，全站 37 處走 `next/image`。
實測線上：

```
/_next/image?url=%2Fimages%2Fcases%2Fcase-1-costco.jpg&w=828&q=75
  帶 AVIF Accept → content-type: image/avif    27,148 bytes
  只吃 JPEG      → content-type: image/jpeg    59,992 bytes
原始 JPG 檔                                   2,456 KB
```

訪客拿到的一直都是 27 KB 的 AVIF。**原始檔是不是 JPG 跟訪客無關**，而把有損 JPG
再轉一次 WebP、再讓優化器轉成 AVIF，等於三次失真。

順帶排除三個可能繞過優化器的路徑：
- 4 處 `style={{backgroundImage}}` **全部是純 CSS radial-gradient**，沒有載入任何圖檔
- 唯一的原生 `<img>`（hero poster）本來就是 WebP + srcSet，註解寫明刻意不走優化器以免產生計費 transform
- `/og-image.jpg` 原檔直出，但只給社群爬蟲且僅 72 KB

> `public/` 底下圖檔原始總量 95.6 MB。這只影響 repo 與部署體積，不影響訪客。
> 壓縮原始檔對訪客零收益、卻有畫質風險，**刻意不動**。

## 3. reduced-motion 的影片閘門（PR #23）

### 問題比第二輪文件寫的嚴重

文件寫「CSS 只是 `display:none`」。實際上 slide 0 的 `<video>` 帶著
`autoPlay={i===0}` 與 `preload="auto"`，跟 reduced-motion 完全無關——
開了「減少動態效果」的訪客**看不到影片，但照樣下載 7.9 MB 並在背景播放**。
元件裡的 `prefersReducedMotion` state 只被拿去停輪播計時器，沒有擋影片。

### 改法：兩個 attribute，不靠 JS

```jsx
<source media="(prefers-reduced-motion: no-preference) and (min-aspect-ratio: 1/1)" … />
<source media="(prefers-reduced-motion: no-preference)" … />
```

開了 reduce 之後沒有任何 `<source>` 命中 → HTML 資源選取演算法停在
`NETWORK_NO_SOURCE` → **零請求**。

**為什麼不用 JS：** JS 方案（`mounted && !prefersReducedMotion`）要等 hydration，
但 SSR 出來的 HTML 已經帶著 `autoPlay preload="auto"`，第一次繪製就開抓，
只能省「大部分」而不是全部。`<source media>` 在 SSR 就是對的。

### 驗收（正式站，含對照組）

| 情境 | mp4 請求 | poster 請求 | networkState | currentSrc |
|---|---|---|---|---|
| 桌機 · 減少動態 | **0** | 3 | 3（無來源） | （空） |
| 桌機 · 一般（對照組） | 3 | 3 | 1 | `hero-cai-mep-1080.mp4` |
| 手機 · 減少動態 | **0** | 3 | 3（無來源） | （空） |
| 手機 · 一般（對照組） | 2 | 3 | 1 | `hero-portrait-720.mp4` |

⚠️ **對照組是必要的**：只量到 reduce 是 0，無法分辨「閘門生效」還是「腳本壞掉」。
截圖確認 reduce 下 hero 完整顯示 poster + 標題 + CTA，沒有開天窗。
對照組同時證明 PR #4 的直式影片行為沒有回歸（手機仍拿 portrait）。

### 已知取捨
- 使用者在頁面開著時切換系統設定，`<source>` 選取不會重算（不重要）
- 不認得 `prefers-reduced-motion` 的老瀏覽器會把整個 query 算成 false，只看到 poster
  （這批人本來就該只看 poster）
- `globals.css` 的 `.bg-video { display:none }` **刻意保留**，現在是雙保險

### 而這三處每一處都是剛修好的競態現場

| 位置 | 為什麼不能照教科書改 |
|---|---|
| `HeroSection.tsx:118` `setIsPortrait` | `matchMedia` 只存在於 client，首次讀取無法在 render 期間推導；且刻意不 bump `rotationKey`（PR #4/#5） |
| `HeroSection.tsx:152` `setMountedMap` | 累積式記憶（「掛過就不拆」），純函數推不出來。搬進事件處理器會失去首次預熱的觸發點，被迫用初始值 `{0:true,1:true}`，那會把 slide 1 的 `<video preload="metadata">` 放進 SSR HTML 提前開抓，**第二輪量到的 3.8 MB 會變** |
| `Navbar.tsx:118` | 路由變更時重置選單狀態。它存在的理由正是 `onMouseEnter` 在 client-side 導航後不會重新觸發 |

改為加 `eslint-disable-next-line` + 理由註解：規則對新程式碼繼續生效，同時讓下一個
看到紅字的人（或 AI）知道不要動它。**僅新增 15 行註解，零邏輯變更、零刪除。**

> ⚠️ 更正第二輪文件 §7：那裡寫「`Navbar.tsx` 89 行」。實際報錯的是 **118 行**、
> 完全不同的一段 effect。89 行那段（捲動量測）根本沒有被這條規則報出來。

> 💡 踩到的坑：`eslint-disable-next-line` 只管**緊接的下一行**。第一次把理由寫在
> 指令和程式碼中間，指令就蓋到註解上——3 個 error 沒消掉，還多出 3 個
> 「未使用的 disable 指令」warning。

## 5. 量過但判定不做：framer-motion 的全站 chunk

`framer-motion` 透過 `Navbar`（14 處）與 `MessageBox` 掛在 `layout.tsx`，
所以**每一頁**都要先下載解析它，而 hero 影片開播、輪播掛載、導覽列量測
全部排在 hydration 後面。這是目前唯一可能再動 FCP 的東西。

實測（手機 390×844，正式站）：

| | 數字 |
|---|---|
| 首頁全部資源傳輸 | 2,189 KB |
| 其中 JS 傳輸 | 291 KB（解壓後 896 KB，14 個檔） |
| 含 framer-motion 的 chunk | 139 KB 未壓縮 → **約 45 KB 壓縮後** |

**佔整頁 2%。** 要換掉等於重寫 Navbar 全部動效、改 UI 行為、需要真人驗收。
**這輪判定不划算，不動。**
