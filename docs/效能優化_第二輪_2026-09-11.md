## 2. ⚠️ 兩件我原本打算做、但實測後發現會做壞的事

這兩件都是策略覆核（Fable）指出、我再自己驗證確認的。記下來，免得以後又想做。

### 2-1 「把第一張影片剪短」是錯的

原本的想法：輪播 10 秒就換頁，影片卻有 28.5 秒，後面 18 秒沒人看得到，剪掉就好。

**錯在兩個地方：**

1. **slide 0 的 `playbackRate` 是 1.25。** 10 秒的顯示時間要吃 **12.5 秒**素材。
   我原本要剪到 11.5 秒 —— 那會在 **9.2 秒就 loop，比換頁還早**，
   變成每個桌機訪客每一輪都看得到接縫。
2. **`onMouseEnter` 綁在整個 `h-screen` 的 section 上。** 桌機訪客滑鼠只要停在首屏
   任何位置，輪播就暫停、影片會一直播下去。所以「看到接縫」是主要路徑，不是邊角案例。

而且實測證明**沒有不明顯的切點**：拿第 0 幀去比 10–20 秒之間每 0.5 秒的畫面，
RMSE 從 69.7 到 74.2 幾乎一樣平——空拍鏡頭已經飄走而且不會飄回來。

**結論：不剪長度，只降位元率。** 位元率降完效果一樣好，而且零接縫風險。

### 2-2 「字集多收一點當保險」會讓檔案變大

原本的想法：只收網站現在用到的字太冒險，多收一批常用字當保險。

實測（全部是可變字型 + woff2 + brotli）：

| 方案 | 字元數 | 大小 |
|---|---|---|
| 現況（Google 版 22 個 chunk） | — | 1,331 KB |
| **只收全站實際用到的字（採用）** | 1,464 | **429 KB** |
| 再加 Big5 常用字當保險 | 5,939 | **1,677 KB** ← 比現況還大 |
| 拆成六個靜態字重 | 1,464 | 1,347 KB ← 等於沒省 |
| 可變軸限縮到 200–700 | 1,464 | 421 KB ← 只省 8 KB，不值得 |

原因：可變字型要為**每一個字**存下各個字重之間的差值，所以字數增加的代價很高。
「保險」的代價是整包大一倍。正確做法是字集抓準，再用建置期檢查擋住日後漏字。

## 3. 🔑 一個跟效能無關、但更重要的發現：全站現在有兩種中文字型

用瀏覽器開發者協定（`CSS.getPlatformFontsForNode`）直接問「這段文字實際用哪個字型畫」：

| 元素 | CSS 裡寫的 | 實際畫出來用的 |
|---|---|---|
| hero 大標題（`.font-sans`） | `Inter` | **PingFang TC** |
| 導覽列「鹿飛 LUFÉ」 | `Inter` | **PingFang TC** |
| hero 副標、輪播文字、內文 | `Inter, Noto Sans TC, sans-serif` | **Noto Sans TC** |

原因在 `globals.css` 的 `@theme inline`：

```css
--font-sans: var(--font-inter);      /* 只有 Inter，沒有接中文字型 */
--font-zh:   var(--font-noto-sans-tc);
```

Tailwind 產出的是 `.font-sans{font-family:var(--font-inter)}`。
`font-sans` 在 `.tsx` 裡用了 66 次、`font-heading` 用了 41 次，這些元素的中文
因為 Inter / Playfair 沒有中文字形，就掉到系統字型去了。

**這會因作業系統而異**：Mac 是 PingFang、Windows 是微軟正黑、Android 是 Noto CJK。
也就是說同一個標題，不同裝置的訪客看到的字體不一樣。

⚠️ **這不是效能優化造成的，在此之前就存在。**
字型子集化**沒有改變**這件事——它只是把 Noto Sans TC 的送達方式從
「Google 切 22 塊」換成「自己家一個檔」。

### ✅ 業主已於 2026-09-11 決定統一成 Noto，已上線（PR #18，`437fbca`）

改法是兩行，把中文後備接進字型鏈本身：

```css
--font-heading: var(--font-playfair), var(--font-noto-sans-tc), sans-serif;
--font-sans:    var(--font-inter),    var(--font-noto-sans-tc), sans-serif;
```

字型 fallback 是**逐字元**的，Playfair / Inter 排在前面，所以拉丁字與數字完全不變。

實測（CDP，改前線上 vs 改後）：

| 檢查點 | 改前 | 改後 |
|---|---|---|
| `/about` 的 h1 | PingFang TC | **Noto Sans TC** |
| 導覽項 | PingFang TC + Inter | **Noto Sans TC** + Inter |
| 統計數字 `42+` | Playfair Display | Playfair Display（不變）|
| 首頁見證 `<q>` | Inter + Noto | Inter + Noto（不變）|

**版面零位移：** 五頁 × 桌機/手機，頁高與所有 `.font-sans` / `.font-heading`
元素的盒子尺寸總和完全相同。也沒有新增流量——Noto 子集本來每頁就在載。

### ⚠️ 過程中發現的兩件事

**1. 字型守門會掃註解。** 我在 `globals.css` 的英文註解裡寫了「微軟正黑」，
build 直接失敗：`軟 U+8EDF` 不在子集裡（全站沒有任何地方用這個字）。
為一句註解重建 429 KB 字型不合理，所以改寫註解。
**日後寫中文註解要注意**——守門不分辨「會不會被畫出來」。

**2. `font-[var(--font-playfair)]` 在 Tailwind v4 是無效的。**
`WhySection.tsx:228` 與 `CaseDetailPage.tsx:274` 兩段客戶見證寫了這個 class，
實測 computed `font-family` 是繼承自 `body` 的 `Inter, …, notoSansTC, …`，
**完全沒有 Playfair**——Tailwind v4 靜默忽略了它（`font-[…]` 無法分辨要設
family 還是 weight）。作者的意圖從來沒有實現。

中文本來就已經是 Noto、沒有壞，所以不是回歸。改成 `font-heading` 可以讓意圖成真，
但那會把這兩段的**拉丁字從 Inter 換成 Playfair**，是視覺變更，**留給業主決定**。

## 5. 字型子集怎麼做的

- 來源：`https://github.com/google/fonts/raw/main/ofl/notosanstc/NotoSansTC[wght].ttf`
  （可變軸 wght 100–900，20,950 glyphs），SIL OFL 1.1，`OFL.txt` 已隨檔附上
- 字集：33 個 prerendered HTML ∪ 全部 `src/**` 的**每一個非 ASCII 字元**
  ∪ 可列印 ASCII ∪ 一批常用標點 = 1,464 個
- 其中字型真的畫得出來的 1,453 個；另外 11 個（9 個 emoji 加 `↺` `▾`）
  Noto Sans TC 本來就沒有，**現在線上也是掉到系統字型**，不是回歸
- 工具：`pyftsubset`（fontTools + brotli），保留完整可變軸

**畫質驗證：** 同樣文字、六種字重（200/300/400/500/600/700）、大小字、CJK 標點，
完整字型 vs 子集字型**逐像素完全相同**（最大差 0、差異像素 0.0000%）。
（同時確認畫面上真的有渲染出中文，不是兩邊都空白才 diff 成 0。）

**防漏字：** `npm run build` 前後各跑一次 `scripts/check-font-subset.mjs`，
掃 `src/` 與產出的 HTML，發現子集外的字就讓建置失敗，並印出修復指令。
負面測試：故意在 `layout.tsx` 塞一個 `齉`，prebuild 如預期印出
`齉 U+9F49 src/app/layout.tsx` 並中止建置。

> ⚠️ **這道守門有代價。** 日後新增任何目前沒用過的中文字（改文案、加新頁），
> `npm run build` 會直接失敗。修法是跑 `npm run font:rebuild` 重做字型檔，
> 再把 `src/app/fonts/` 底下兩個檔一起 commit。
> 需要先 `pip3 install fonttools brotli`。錯誤訊息裡有寫這串指令。

**視覺回歸：** 1440×900 DPR2，四頁全頁截圖，逐像素比對 main vs 字型分支
（兩台 `next start`，先把整頁捲過一遍讓懶載入圖片載完、等 `document.fonts.ready`、
把影片定格在同一格）：

| 頁面 | 平均差 | 最大差 |
|---|---|---|
| home | 0.00024 | 69（唯一差異是影片畫格） |
| services | **0** | **0** |
| insights | 0.000026 | 1 |
| about | **0** | **0** |

### ⚠️ 這個比對第一次跑出來是錯的，記一下教訓

第一次跑出「about 有 91.4% 的像素不同、平均差 122/255」，看起來像重大回歸。
實際上是**量測本身壞掉**，而且壞了三層，一層一層剝掉才看到真相：

1. **抓到的根本不是那一頁。** 存檔名字寫 about，畫面卻是首頁。
   原因是 `/about` 有背景影片，`waitUntil: 'networkidle'` 永遠等不到，逾時後拍下了錯的狀態。
   → 改成 `domcontentloaded` + 明確斷言每頁的 `h1` 文字。
2. **懶載入圖片兩邊載到的張數不一樣。** 兩台都只拍首屏，捲不到的照片有的載了有的沒載。
   → 改成先把整頁捲過一遍，再等所有 `<img>` 的 `complete`。
3. **其中一台的 `next/image` 優化器卡死了。** 兩張圖固定 30 秒不回應（另一台 2 毫秒），
   清了快取還是卡；**重啟該台伺服器後 0.8 秒就回來，位元組數與另一台完全一致**。
   跟字型無關，是長時間執行的 dev server 自己卡住。

判斷這種事的關鍵是**對照組**：拿同一台伺服器自己跟自己比。
對照組跑出 services/insights/about 都是 0，才證明「那 11.8 不是雜訊」，
逼我繼續查下去而不是當成隨機誤差帶過。

## 6. 進度條修了什麼

兩個 bug：

1. `globals.css` 的動畫是 **7000ms**，但 `AUTOPLAY_MS` 是 **10000** →
   進度條 7 秒跑滿、呆坐 3 秒才換頁
2. `progressKey.current += 1` 寫在 **render body** 裡 →
   註解說「每次換頁」，其實是「每次 render」。切片的頭一秒內
   `mountedMap` 與 `readyMap` 各觸發一次 re-render，進度條會歸零重跑兩三次

實測（格寬 424 px，每秒取樣）：

| 秒 | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|---|
| px | 67 | 110 | 152 | 195 | 237 | 280 | 322 | 365 | 407 |

每秒約 42.5 px → 10 秒跑完，**全程單調遞增、一次都沒歸零**。

### ⚠️ 已知限制（沒修）
`animate-hero-progress` 這個 class 在 SSR 出來的 HTML 裡就有，CSS 動畫在第一次繪製就起跑；
而 `setTimeout(AUTOPLAY_MS)` 要等 hydration 之後才起跑。所以**第一輪**進度條仍會比換頁
早 1–3 秒跑滿。這不是「不可能再漂移」，只是差距從 3 秒變成 1–3 秒且只發生在第一輪。
