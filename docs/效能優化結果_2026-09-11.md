### 3-1 為什麼「等 JS 判斷方向再給 src」不行（#10）

原本用 `isPortrait` 這個 React state 決定播哪支影片。問題是 SSR 時它必定是 `false`，
所以**伺服器送出的 HTML 裡就寫著桌機影片**，而且帶 `preload="auto"`。
瀏覽器的 preload scanner 在 0.1 秒就開始抓，**那時 React 根本還沒執行**。

所以解法不能停留在 JS 層，必須讓 HTML 本身就選對檔：

```tsx
<source media="(min-aspect-ratio: 1/1)" src={slide.media.src} type="video/mp4" />
<source src={slide.media.portraitSrc ?? slide.media.mobileSrc ?? slide.media.src} type="video/mp4" />
```

**橫式那行刻意放前面。** 萬一某個瀏覽器不認 `media` 屬性，所有人都會拿到橫式
＝維持現狀；反過來寫的話，失敗模式會變成「桌機播到直式影片」，那更糟。

另外加了一個 `rotationKey`，只有**真的旋轉**才會 +1。
初始那次不動它，這樣 hydration 之後 `<video>` 不會重新掛載、
不會把已經在下載中的正確檔案砍掉重抓。

### 3-2 CSS 背景圖繞過了整個圖片最佳化（#11）

```tsx
// 改前
<div style={{ backgroundImage: `url('${slide.media.poster}')` }} />
```

CSS 背景圖是**一個寫死的 URL**，不轉格式、不依裝置出圖。
等於把 4096×2160 的原始 JPG 直接送給 390px 寬的手機。
改成 `<img srcSet sizes="100vw">` 之後瀏覽器自己挑尺寸。

⚠️ 省多少要用 **1600w** 那一階算：手機 390 CSS px × DPR 3 = 1170 裝置 px，
瀏覽器挑「不小於 1170」的最小一階，所以中的是 1600w 不是 828w。

## 4. ⚠️ 為什麼 Lighthouse 分數沒有進步（這一節很重要）

| | 改前 | 改後 |
|---|---|---|
| 效能分數 | 57 | 56 |
| LCP（模擬） | 18.8 s | 10.9 s |
| FCP（模擬） | 8.0 s | 7.9 s |

分數是由 FCP 等指標加權算出來的，而 FCP 沒動，所以分數沒動。

**但 FCP 從頭到尾就不是真的 8 秒。** 用真實瀏覽器在同樣的節流條件下量：

| | 改前 | 改後 |
|---|---|---|
| 真實 FCP | 1,496 ms | 1,520 ms |

差了五倍。原因是 Lighthouse 預設用 **Lantern 模擬器**：它只跑一次不節流的載入，
再用模型「推算」在慢速網路下會是多少。這個模型不知道影片對首次繪製沒有影響，
會把它算進頻寬競爭裡。

實測佐證（真實瀏覽器，1.6 Mbps 節流）：

| 情境 | FCP |
|---|---|
| 現況 | 1,588 ms |
| 擋掉全部字型 | 1,352 ms（字型只值 236 ms） |
| **擋掉全部影片** | **1,588 ms（完全沒有影響）** |

**判讀原則：想知道使用者體驗如何，看「真實瀏覽器量到的數字」與「總傳輸量」，
不要看 Lighthouse 的模擬分數。** 這次真正改善的是流量（−85%）與整頁載完時間
（15 秒內沒載完 → 10.5 秒載完），那才是訪客真正感受得到的。

### 順帶：LCP 元素不是 hero

`nav.transition-all > div.max-w-[1400px] > a.flex > span`，也就是導覽列的
**「鹿飛 LUFÉ」那行字**。Chrome 計算 LCP 時會排除滿版背景元素，
以及從 `opacity: 0` 動畫進場的元素——hero 兩個條件都中。
所以「改 hero 來修 LCP」這個方向本身就是錯的。

## 6. 還沒做的事

### ① 字型 1,331 KB（最大的一筆，但有視覺風險）

**根因跟稽核時寫的不一樣，這裡更正。** 稽核當時寫「6 個 woff2 約 450 KB」是錯的，
實際是 **22 個 woff2 共 1,331 KB，全部是 Noto Sans TC**。

`layout.tsx` 三個字型都**沒有指定 `weight`**，所以 `next/font/google` 載入的是
可變字型全軸。Next 會依 `unicode-range` 切成 116 個 chunk，瀏覽器只抓用得到的那些——
問題是中文字散落在很多個 range 裡，**常常為了幾個字就抓一整塊 65–85 KB**。

真正的解法是「照網站實際用到的字做子集化並自架」，可能壓到 100–150 KB。
但風險是：**只要有一個字沒被收進子集，那個字就會掉成系統字體**，
句子中間出現不同字體會很明顯。洞察文章、表單輸入都可能出現沒預期到的字。

⛔ **這件事不要順手做。** 要做的話得先把全站文字盤出字集、留保險的 fallback、
並且逐頁目視驗收。

補充：`display: swap` 已經有設，實測字型只讓 FCP 慢 236 ms，
所以這件事是「省流量」，不是「修速度」。

### ② 第一張影片有 28.5 秒，但訪客只看得到前 10 秒

`AUTOPLAY_MS = 10000`，切走再回來會 `currentTime = 0`。
所以 **後面 18 秒的畫面沒有人會看到**，那部分位元組是純浪費（約佔該檔 65%）。

⚠️ 但**不能直接剪掉**：滑鼠停在 hero 上會暫停輪播，這時影片會繼續播下去。
剪短之後那位訪客會看到影片跳回開頭，而空拍前進的鏡頭跳接會很明顯。

要不要做，看你要不要接受「停在 hero 上的訪客會看到一次跳接」。
